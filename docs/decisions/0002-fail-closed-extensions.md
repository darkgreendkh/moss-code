# 0002 · 外部能力一律 fail-closed

- **状态**：已采纳
- **影响范围**：MCP、skills、code mode、用户钩子、delegate
- **相关**：[0001](0001-zero-dependencies.md) · [features/tool-safety.md](../features/tool-safety.md)

## 决定

任何来自 moss 之外的能力，在**声明不完整、前置条件不满足或信任状态改变**时，
一律**拒绝启用并报错**，而不是降级到一个"能跑但少点东西"的状态。

具体：

| 场景 | 行为 |
| --- | --- |
| MCP 工具没在 `.moss/config.json` 声明 capabilities | 拒绝注册 |
| MCP 工具 | 一律额外加隐含 `network` 能力并标 risky |
| skill 的 `allowed-tools` 越出 run 级白名单 | 拒绝点亮，**不静默取交集** |
| 第三方 skill 的内容指纹变了 | 首次使用要用户确认 |
| code mode 没有可用沙箱 | 不暴露 `run_orchestration`，即使 `--enable-code-mode` 开着 |
| risky 工具没声明能力标签 | `policy` 直接拒绝 |
| delegate 的能力超出父集 或 越出只读边界 | 拒绝 |
| 证据锚点指不到工作区内的文件 | 丢掉锚点只留结论 |

## 为什么不降级

降级看起来更"友好"，但它把一个**显式的配置错误**变成了一个**隐式的行为错误**。

### skill 的例子

一个 skill 声明 `allowed-tools: [run_shell, read_file]`，
意思是"做这件事需要跑命令"。如果 run 级白名单里没有 `run_shell`：

- **静默取交集** → skill 带着只有 `read_file` 的能力去干活。
  它会读一堆文件，然后基于"我没法验证但看起来没问题"给出一个结论。
  **这个结论是错的，但整个过程看起来是成功的。**
- **拒绝点亮** → 用户立刻知道"这个 skill 在当前配置下用不了"。

后者最坏是多一次配置往返，前者最坏是一个看不出来的错误答案。

### 沙箱的例子

`--enable-code-mode` 的语义是"我允许模型写一段脚本批量编排工具"。
用户按下这个开关时的心智模型里，**沙箱是配套存在的**。
沙箱不可用时还暴露 `run_orchestration`，等于在用户不知情的情况下
把风险等级提高了一档。所以沙箱是**硬前置**，不是"最好有"。

### 能力标签的例子

新加一个 risky 工具却忘了写 `capabilities`，如果 fail-open，
它会以"没有任何能力要求"的身份通过所有策略检查——
`--deny network` 拦不住它，`--allow fs_write=src/**` 也约束不了它。
fail-closed 让这个疏忽在**测试里立刻炸掉**。

## 例外：只收紧不拒绝

有一类情况不适用这条决策：**误报率高、且后果可控**的检测。

`injection.py` 命中时**不拒绝执行**，只是把本 run 剩余的 risky 工具改成强制审批。

原因：正常代码里就有 `"ignore previous instructions"` 这样的字符串，
误报是必然的。把误报变成"任务直接失败"比漏报还难受。
而"接下来都要问一次"这个后果对真攻击有效、对误报只是多按几次 y。

判断标准是：**这个检测的误报会不会让正常工作变得不可能。**
能力声明缺失不会误报（它是确定性的），所以 fail-closed；
注入检测一定会误报，所以只收紧。

## 配套要求

fail-closed 只有在**报错信息说得清**的时候才好用。所以：

- 拒绝时必须说明拒的是什么、缺的是什么、怎么补。
- 拒绝要留痕（`hook_denied` 等 trace 事件）——
  一次被悄悄拒掉的调用，表现是模型莫名其妙地绕圈，极难排查。
